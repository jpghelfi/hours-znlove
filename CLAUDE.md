# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A time tracker where **Notion is the database / source of truth**. Two Notion databases (Projects, Time Entries — plus an optional Allocations one for the schedule/forecast view) live under a "Hours Tracker" page. On top of that:

- `web/` — FastAPI + Jinja2 + HTMX web app (log hours form, editable Mon–Fri weekly grid, reports with CSV export, per-project hours by month/week/day, schedule/allocations grid, start/stop timer). Deployed on Render free tier (`render.yaml`), live at hours-znlove.onrender.com.
- `src/` — Python CLI scripts: one-time schema setup, project seeding, backfill logging, reports.

No linter is configured. The only tests are `tests/test_budgets.py` — plain asserts and a
tiny runner, deliberately no pytest dependency; they cover the budget arithmetic and never
call Notion.

## Commands

```bash
# setup
python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt

# run the web app locally (AUTH_DISABLED=1 in .env bypasses Notion OAuth — local dev only)
./.venv/bin/uvicorn web.app:app --reload

# CLI scripts (all read .env + databases.json via src/config.py)
./.venv/bin/python src/setup_databases.py          # one-time: creates the Notion DBs, writes databases.json
./.venv/bin/python src/setup_people_db.py          # creates + seeds the People roster db (idempotent; re-run to add new members)
./.venv/bin/python src/setup_absences_db.py        # creates the Absences db (idempotent)
./.venv/bin/python src/seed_projects.py "Name" …   # dedupe-safe bulk add
./.venv/bin/python src/log_hours.py --project X --hours 2.5 --desc "..."
./.venv/bin/python src/report.py [--by project] [--since YYYY-MM-DD]

# tests (no pytest; hits no network)
./.venv/bin/python tests/test_budgets.py
```

## Architecture

- **Notion 2025-09-03 API** (notion-client ≥ 3): every database wraps a *data source*. Schema lives on the data source, new pages parent to `data_source_id`, queries go through `notion.data_sources.query`. Keep using this style — don't fall back to the older `databases.query` API.
- **ID resolution** (`src/config.py:load_db_ids`): locally, ids come from `databases.json` (gitignored, written by `setup_databases.py`); on Render they come from env vars (`PROJECTS_DS_ID`, `TIME_ENTRIES_DS_ID`, `ALLOCATIONS_DS_ID`, `PEOPLE_DS_ID`, plus `*_DB_ID`). Env vars override the file. New databases must be wired into both paths.
- **People roster** (`list_people` in `web/notion_ops.py`): the people shown everywhere (assignments columns, schedule rows, dropdowns) come from the **People** database (curated in Notion: untick `Active` to hide — don't delete the row, re-running the seeder would re-add them; row title renames; `Person` link is required). When `people_ds_id` isn't configured — or the roster query fails (e.g. bad `PEOPLE_DS_ID`) — it logs and falls back to listing all workspace members rather than 500ing. New workspace members don't appear until `setup_people_db.py` is re-run or a row is added by hand.
- **Access control lives in the People db** (`access_ids` in `web/notion_ops.py`, consumed by `auth.is_allowed`/`is_admin`): who may log in and who is admin is curated in Notion, matched by the linked `Person`'s Notion user id (the same id OAuth returns) — **not** by email. `Active` = can log in; the `Admin` checkbox = team-wide reports/exports scope. The derived id sets are TTL-cached (~60s) since `is_admin` runs several times per request, so Notion edits take up to a minute to take effect. `is_allowed` is re-checked on every request too (via `_require_login` in `app.py`, reusing the cached sets), so unticking `Active` ends a live session within the TTL — not just future logins. `ALLOWED_EMAILS` / `ADMIN_EMAILS` env vars remain a **fallback** (OR'd in) so a People-db misconfig can't lock everyone out; on query failure the check degrades to env-only. Add a person by giving them an Active People row (`setup_people_db.py` or by hand); revoke by unticking Active.
- **`web/` imports from `src/`**: `web/notion_ops.py` does `sys.path.insert` to reuse `src/config.py`'s client and id loading. All Notion reads/writes for the web app live in `notion_ops.py`; `web/app.py` holds only routes/HTTP concerns.
- **Auth** (`web/auth.py`): Notion OAuth is used for *identity only* — the authorizing user's identity is checked against the People-db roster (Active row = allowed, Admin tick = admin; see "Access control" above), with `ALLOWED_EMAILS`/`ADMIN_EMAILS` as a fallback. All data access then uses the internal integration token (`NOTION_TOKEN`). `is_allowed`/`is_admin` take the **user dict** (`{id, email}`), not a bare email, so they can match by Notion id. Mutating routes check same-origin (`_same_origin` in `app.py`) as CSRF protection.
- **Who logged an entry**: web-app entries write an explicit `Person` (people) property (re-added on startup by `ensure_person_property` if missing); Notion-form submissions rely on the auto-filled `Logged by` (created-by) property; CLI entries have no human submitter. Readers (`report.py`, the weekly grid) must handle both `Person` and `Logged by`.
- **Weekly grid** (`/week`): cell edits are upserts keyed on (person, project, date); hours = 0 deletes the entry.
- **`/schedule` is readable by everyone, plannable only by admins**: a non-admin gets the page pinned to **their own row** — the route sets the people pick to their Notion user id and **drops any `?person=`** they send, so a hand-typed id shows their own week. Read-only there means the affordances are *gone*, not disabled: no cell click target, no `+`, pills are `<span>`s not `<button>`s, no Copy/Clear week, no assign dialog, and none of the popover JavaScript (which also keeps the roster and project-membership lists out of a page with no use for them). The three write endpoints already refused non-admins; the UI gating is what stops the page offering a click that could only 403. A **single** person pick is the one filter pushed into the Notion query (`alloc_rows`) rather than filtered in Python — it's every non-admin's view of this page, so it's the read that got the traffic when the page opened up.
- **Schedule / allocations are day-first** (`/schedule`, planning is admin-only): every allocation row carries a real weekday date (the Notion property is still named `Week`). There is no week-scope write — `ops.set_allocation_range` upserts one row per weekday in a range and skips weekends, taking `_write_lock` once for the whole range; `hours = 0` deletes those days. The **Days** view is the planner: one row per person (or per project), each day cell a stack of project pills, so several projects can share a day; a click opens the assign popover (project + hours/day + "repeat through"). The **Weeks** view is a read-only six-week rollup that buckets each day into its Monday. Capacity is `DAY_TARGET_HOURS` (default 8; `WEEK_TARGET_HOURS` still overrides the weeks rollup's number). Booking someone onto a project also adds them to its `People` property, so `/schedule` and `/assignments` can't drift. Allocations written before the day-first planner sit on a Monday and simply read as hours on that Monday. **Copy last week** (`POST /api/allocation/copy-week` → `ops.copy_week_allocations`) lifts the previous week's bookings onto the week on screen, weekday for weekday: additive, so a (person, project, day) pair present in both takes the source week's hours and anything else already in the target week survives. It honors the page's current person/project filters — the button copies what you can see — and refuses to write more than `MAX_COPY_ROWS` (500) bookings at once. **Clear week** (`POST /api/allocation/clear-week` → `ops.clear_week_allocations`) is the destructive counterpart: it wipes every booking Mon–Fri of the week on screen, under the same filters (so a filtered view only deletes what it shows) and the same 500-row cap, checked before the first write so a too-big week is refused whole rather than half-deleted. It archives by **page id** — the rows `alloc_rows` just returned, which is why that read now carries `id` — instead of re-deriving (person, project, day) upsert keys, so a duplicate row left by an old race goes too instead of surviving as a ghost. There is no undo; the confirm dialog is the only guard. **A booking can also be dragged** (`POST /api/allocation/move` → `ops.move_allocation`): onto another day, another row, or both — ⌥-drag copies instead of moving. The hours are re-read from Notion rather than sent by the browser (a pill can be a fold of duplicate rows, and it can be stale), and landing on a day that already books the same pair *adds* to it; target write and source delete share one `_write_lock`. **The drop is optimistic**: the pill lands on the next frame and the Notion round-trip runs behind it, with the pre-drop hours of *both* pairs captured first — a refusal or a dead connection repaints the week exactly as it was and explains itself in a dialog, and the server's numbers are laid over the guess when they arrive (so a concurrent edit can't leave a wrong total on screen). The waiting pill wears a quiet `.is-pending` outline. While a drag is live the cell's `+` and `×` get `pointer-events: none` — a drop that lands on a `<button>` is refused by the browser and the pill snaps back, and the `+` sits exactly where an empty cell invites you to aim; the pills themselves must keep their pointer events, since taking them away mid-drag cancels the drag outright. **Editing a booking can change its project too**: the popover's select stays live, and the save carries `from_person_id`/`from_project_id` so the route clears the old pair over the same weekday range (new booking written first, the clear outside its `try` — a day showing both is visible and fixable, the other order could drop the hours). Swapping onto a project the day already books *replaces* its hours, so the browser confirms first. **Bookings can be selected and pasted onto other days** (`POST /api/allocation/paste` → `ops.paste_allocations`): ⌘-click pills (⇧ extends, ⧉ takes the whole cell — the touch way in, since ⌘-click has no equivalent there), then every other day cell is a target and one click writes them all; the selection stays live so several days are several clicks, ⌘V pastes into the day under the pointer, Esc clears. A selection is deliberately confined to **one cell** — (row, day, pairs) is exactly what a paste replays. **A paste *sets* where a drag *adds***: dropping 3h of Kepos onto a day holding 2h means 5h (those hours moved), but pasting Kepos 6h onto a day holding 2h means 6h ("make Wednesday look like Monday" is a statement about Wednesday) — and only the pasted pairs are touched, since wiping a day is Clear day. The browser resolves the grouping before sending, so the endpoint only sees finished (person, project) pairs and works identically in both views; `_write_lock` is taken **per day, not per paste**, so a big paste can't freeze every weekly-grid save meanwhile. **Three sizes of delete share one function** (`ops.clear_allocations(date_from, date_to, person_ids, project_id)`): `×` on a cell (that row, that day), 🗑 under a day's date (the whole column), Clear week (Mon–Fri) — all under the page's filters, all deleting by page id. **The day headers stay put** because the planner grid is now its own viewport-bounded scroller (`.plan-scroll`), *and* sticky itself under the top bar — `.grid thead th` was always `position: sticky`, but a wrapper that never scrolls vertically gives sticky nothing to stick to. `base.html` measures the top bar into `--topbar-h`, since it wraps to two lines on a narrow window.
- **The Allocations people column is resolved by schema, not by name** (`alloc_person_prop` in `notion_ops.py`): the Notion API addresses properties by name, so renaming that column in the Notion UI once took down `/schedule` *and* `/reports` with a `KeyError` (it had been renamed to `val`). Every allocation read/write now asks the data source for its people property — preferring `Person`, falling back to the only people-typed column, cached ~5 min — and logs a warning naming the rename. Renaming it back in Notion is still the right fix; the resolution just stops a stray keystroke from 500ing two pages. Time Entries doesn't need this: `ensure_person_property` re-adds `Person` on startup and readers already fall back to `Logged by`.
- **People properties come back nameless**: Notion returns `{"object": "user", "id": …}` with no name for people properties, so anything showing a person's name must resolve it against the roster (`_person_name_map` in `notion_ops.py`, or the `people` list already loaded by a route) rather than trusting the payload.
- **People filter** (`web/templates/_people_filter.html`): one shared `<details>` dropdown of checkboxes named `person`, included by both `/reports` and `/schedule` (with `{% with selected = … %}`) so the two can't drift. Both routes accept repeated `?person=<notion user id>`; no pick means everyone, and the picks ride along on every nav link/export via a `qs_person` loop. `/schedule` filters its allocations in memory against the pick (the Notion query stays unfiltered) and only draws skeleton rows for the picked people. **A view narrowed to one project drops the rows that came out empty** (`_schedule_rows` returns `(rows, hidden)`): the Fotosprint week means the people on Fotosprint, not the whole roster with four filled rows — and symmetrically for project rows under a people pick. An explicit pick is never pruned. Since an empty row is the only way to book someone new, the page names what it hid and links back to the unfiltered planner.
- **Reports scope rules**: `_report_data` filters entries *and* allocations in memory (the Notion query stays unfiltered) and a non-empty pick implies team scope — so the pick is honored for admins only, and ignored for everyone else. Cross-breakdowns (`_person_projects`, `_person_project_matrix`) are derived from the same filtered entries; both sort by hours desc, tie-broken by name.
- **Per-project view** (`/project`, admins): **one** period (a month, a week or a day — not a window of several), either rolled up across all projects or drilled into one. `_period_range` in `web/app.py` owns all three granularities: it returns the date bounds, the label, the prev/now/next anchors and which native picker to show (`date` vs `month`), so adding a granularity is one branch there. `?start=` is the anchor — `_project_anchor` widens the month picker's `YYYY-MM` to the 1st before parsing. `?project=` **repeats** (a multi-select mirroring the people filter, `web/templates/_project_filter.html`): no pick — or the legacy `all` — is the every-project rollup, one pick drills into that project, several roll up just those. `_project_picks` resolves the params (unknown ids are dropped, so a stale link degrades to the rollup). The two modes read differently on purpose: one project goes through `ops.project_entries` (filters on the Project relation *in the Notion query*), while the rollup uses a single `entries_between` for the period and groups by `project_id` in Python — one read for every project instead of one query each; a multi-pick filters that same read in memory (`keep_ids`), so narrowing costs no extra round trips. `/project.csv` takes the same repeated `?project=` and exports exactly the filtered rows.
- **Inline hours edits are per *entry*, admins only** (`POST /api/entry/hours` → `ops.set_entry_hours`): the entry list at the bottom of `/project` renders each row's Hours as an input, so an admin can correct a wrong number where they spotted it. Addressed by the entry's **page id** (now returned by `entries_between`/`project_entries`) rather than by the (person, project, date) upsert `/api/cell` does — an aggregate row can't be edited inline without inventing how to split the change across days, and `/api/cell` deliberately only ever writes the caller's own hours. `0` archives the entry (same rule as a blanked weekly-grid cell). Because the id is client-supplied, `set_entry_hours` retrieves the page and refuses anything whose parent isn't the Time Entries data source. The tables above the list are server-rendered aggregates, so a save reveals a sticky "totals are stale · Refresh" bar instead of silently leaving old sums on screen. Each **person row is a disclosure over their own entries** (`log` on the row, built by `_project_hours` and `_all_projects_hours` alike), rendered by one `entry_row` macro with the same editable Hours cell — so the same entry id appears twice on the page and `saveEntry()` updates or removes every `tr[data-entry=…]`, not just the one that was typed in. In the rollup that nests two deep (project ▸ person ▸ entries): entry rows there are keyed to their person by `data-parent` instead of carrying `sub-row`, so the project disclosure toggles only the person rows — and closing a project explicitly hides the entries under it and resets the person carets, or a reopened project would spill every entry back onto the page.
- **The shareable export** (`/project/export`, admins): the client-facing counterpart to the inline editor. `/project.xlsx` downloads the report as a grouped workbook straight away (`web/report_xlsx.py`: a Summary sheet when more than one project, then one sheet per project — a title block, a by-person table, and the full log with every entry's comment); `/project/export` first lets the sender adjust the numbers and reword comments, then download **or email** it. Those adjustments live only in the POSTed payload (`_rows_from_payload`) — they are never written to Notion, which is the whole point of the screen: `/api/entry/hours` fixes what was *logged*, this fixes what a client *sees*. A row set to 0 drops out of the file. All three exports (`csv`, `xlsx`, the send) read through `_period_entries`, so they can't disagree about what the period and the project picks mean.
- **Two ways into a Google Sheet, picked by whether Google is connected**: with `GOOGLE_*` set, `POST /project/export.gsheet` → `report_gsheet.create` builds the file itself — titled `<label> - Hours - <period>`, a Summary tab plus one per project, header rows bolded, columns auto-sized — and returns its URL. Without it, **Copy & open Google Sheets** falls back to the clipboard: the rows as TSV plus `sheets.new` for a ⌘V (synchronous `execCommand('copy')` first, precisely so the click still counts as user activation when the tab opens; `navigator.clipboard` as fallback; a blocked popup is reported, not swallowed). Google publishes no URL that creates a spreadsheet holding your data, and the app sits behind a login so `IMPORTDATA` can't fetch from it either — the API is the only way to do this properly.
- **One Google authorization for both features** (`web/google_auth.py`): Gmail send and Sheets create share a refresh token and its cached access token, so `src/google_oauth_setup.py` asks for `gmail.send` *and* `drive.file` in one consent. `drive.file` is the narrow scope — it reaches only files this app created, never the rest of the Drive. `google_auth.call()` centralizes the one forced token refresh on a 401 and turns Google's error payloads into a sentence.
- **Emailing reports is behind an off-by-default switch** (`REPORT_EMAIL_ENABLED`, read by `mailer.enabled()`): the export screen renders the To/Subject/Send controls only when the switch is on *and* a transport is configured, and `POST /api/report/email` returns 403 while it's off. The switch is deliberately separate from the credentials, because the same `GOOGLE_*` authorization powers the Sheets export — connecting Google for sheets must not resurrect an email UI nobody asked for. Turning it on is one env var; the code path is intact and tested.
- **Email goes out through the Gmail API, not SMTP** (`web/gmail_api.py`, chosen by `mailer.transport()`): **Render's free instances block outbound ports 25/465/587**, so every SMTP send from the deployed app dies with `[Errno 101] Network is unreachable` — a different password, or SMTP with OAuth (XOAUTH2), fails identically because the block is on the port. The Gmail API is HTTPS on 443. It also sidesteps app passwords, which this Workspace has disabled, and files the message in the sender's real Sent folder. Config is `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GOOGLE_REFRESH_TOKEN`, minted once by `src/google_oauth_setup.py` (loopback OAuth on localhost:8765; the consent screen must be **Internal**, or the refresh token expires after 7 days). Access tokens are cached in-process and a 401 buys exactly one forced refresh. The SMTP path is still in `mailer.py` for a paid instance or a local run. `REPORT_TO` seeds the recipients (zarco@ and angie@znlove.xyz), editable per send, validated and capped at 10; `REPORT_FROM` pins the From address, and without it Gmail fills in the authorized account. Nothing is queued or retried — a send either completes inside the request or reports Google's own words via `mailer.explain()`.
- **A logged entry can carry the Notion ticket it was for** (`docs/notion-task-links.md`): two plain properties on Time Entries — `Task URL` + `Task` (label), added by `ensure_task_properties`, never a relation because a relation targets one data source and znlove's tickets live across many boards. The two ways in need very different things from Notion, which is the whole design: **pasting a link needs no permission at all** (a Notion URL carries the page id *and* the title in its slug, so `parse_task_url` resolves it offline — `app.notion.com` today, `notion.so`/`notion.site` too; `?v=` board links and our own pages are refused), while **search needs the integration connected to the ticket boards** (one admin action per top-level page; access inherits to every child). Until then `task_sources()` is empty and the picker says so instead of erroring. `TASKS_DS_IDS` names the boards outright, skipping discovery — worth setting, since discovery leans on Notion's search index, which lags. Search is scoped by the ticket's **assignee** (`_assigned_to`: a people property matched on the asker's Notion user id, or an email/text property on their address), with the assignee and title properties resolved from each board's schema rather than by name — other teams rename their columns (the `alloc_person_prop` lesson). That scoping is a convenience, not a permission boundary: search runs with the app's view of Notion, not the asker's. **A third way in creates the ticket** (`ticket_create_enabled`/`create_ticket`, `POST /api/tasks/create`): ＋ New ticket by the picker's label opens a dialog (title required, description, project) and drops the new page straight into the chip. It needs *write* access to exactly one board, named by `TICKET_CREATE_DS_ID` and never by the browser — so the button doesn't render until that's set. Title/assignee/project are resolved from the board's schema, the description becomes the page **body** (these boards have no description property), and status/type/priority are left to the board's defaults. The project column is a `select` owned by another team: only **18 of our 35** active projects had a matching option, so the dialog offers the board's real options — preselected when ours matches on case/punctuation alone (`_norm`: `FShip`→`Fship`), blank otherwise. An unmatched name is never written, because Notion *creates* a select option for any name it doesn't know; and matching is deliberately no fuzzier, since our `Saltworks` vs the board's `Salworks` would file a real ticket against the wrong client. **That dialog renders outside the entry form** (`_task_dialog.html`, via base.html's `modals` block): inside it, its `required` Title was validated on every *Save entry* while invisible in a closed `<dialog>`, so the browser refused the submit and had nothing to focus to say why — logging hours silently did nothing for everyone the day `TICKET_CREATE_DS_ID` was set. Nothing `required` goes inside a form unless it's visible; base.html now surfaces an invisible invalid control instead of letting a save fail in silence.
- **Invoices record what was billed, never what was logged** (`docs/invoices.md`, `/invoices` + `POST /api/invoice`, admins): a third layer on top of the two that already existed — `/api/entry/hours` fixes what was *logged*, the export screen adjusts what a client *sees* for one send, and an invoice records what was *billed*. Only the first touches a Time Entry. Viewing one project on a monthly period turns the export button into **Invoice** and the same screen grows two hour columns (`Tracked`, read-only from Notion; `To bill`, editable, defaulting to tracked). Stored in a separate **Invoices** database (`src/setup_invoices_db.py`; `INVOICES_DB_ID`/`INVOICES_DS_ID` on Render, both id paths as always) with the month as the **1st as a real date**, tracked and billed hours, an editable `Issued` date and who saved it. `save_invoice` **upserts on (project, month)** — a second save is a correction, not a second bill — and the screen names what's on file before replacing it. The billed total comes from the browser (it's the human decision) but **the tracked total is re-read from Notion**, because a row zeroed on the export screen drops out of the file and would otherwise shrink what we claim was tracked. Since tracked is stored, `/invoices` flags a month whose logged hours moved after invoicing — computed for the last four months from one read of that window, not one query per invoice. Everything degrades quietly when the db isn't configured (`invoices_enabled()`). No rates or amounts: this bills hours, not money. **Clicking an invoice opens `/invoices/{id}`** — the month day by day, tracked beside billed, adjusted lines marked and unbilled ones struck through. That works by storing **only the lines that differ** (`Adjustments`, `{entry id: billed hours}`, chunked across rich-text objects, rewritten on every save so a line billed back at its logged hours stops being an adjustment); opening an invoice re-reads the month and lays those overrides back over it, so the detail shows *today's* entries rather than a frozen copy. Invoices saved before this existed have no breakdown and say so instead of showing days that contradict their own total. `get_invoice` refuses any page whose parent isn't the Invoices data source, since the id comes from a URL.
- **Absences are one row per absence, not per day** (`docs/absences.md`, `/absences` + `POST /api/absence/delete`, everyone): the opposite storage choice from allocations, and deliberately — an absence is one decision with one reason, so a fortnight off is a single row whose Notion `Dates` property carries start *and* end (plus `Days`, the weekday count, so the Notion table shows what it costs). Logging one never asks *who*: it's always the logged-in person, like `/api/cell`. `ops.list_absences` returns absences **overlapping** the period, which Notion can't fully filter — its date filters compare against a range's *start*, so the query reaches back a bounded window (`_MAX_ABSENCE_DAYS`, 366) and settles the far edge in Python. `_absence_days` in `app.py` expands rows into weekdays **clipped to the period**, so a straddling absence counts only the days inside it and two overlapping absences can't count one day twice. The dashboard is one period at a time (`_period_range` reused): weekly = Mon–Fri columns, monthly = the weeks touching the month, since 22 weekday columns don't read. Admins see everyone plus the shared people filter; everyone else sees only their own (the pick is dropped server-side, not just hidden). Deleting checks the page's parent data source *and* ownership before the write — `any_person` is the admin's escape hatch. Created by `src/setup_absences_db.py`; `ABSENCES_DB_ID`/`ABSENCES_DS_ID` on Render, and `absences_enabled()` degrades the page quietly until then. No approval flow, no allowance, and **no effect on `/schedule` or reports yet** — booking someone who's away is still allowed.
- **Project budgets are settings on the project, not a database** (`docs/budgets.md`, `/budgets` + `POST /api/budget`, admins): an optional **monthly** hour allowance per project that resets on the 1st and never carries over, plus a policy for what happens when it runs out. Stored as four properties on the Projects data source (`ensure_budget_properties`, added at startup like `ensure_person_property`) rather than in a db of its own — exactly one value per project makes it configuration, not the dated events invoices and absences are — which also means it rides along on the `list_projects` query the app already runs, so a check costs no extra read. **Empty ≠ 0**: empty means unbudgeted, `0` means no hours allowed at all (Harvest's documented trap). Two properties cover all three behaviours: `Budget policy` = `Warn only` (no limit) or `Block over limit`, with `Overrun %` blank for a hard stop at the budget and `10` for a stop at 110%. Read through `.get()` throughout (`_budget_from_props`), so a renamed column reads as "no budget" instead of 500ing the way the `alloc_person_prop` rename once did. **Admins are never blocked** — a cap binds non-admins only, since admins are the people who can change the budget — which removes a chokepoint instead of adding a branch: `/api/entry/hours` is already admin-gated and needs no check, so enforcement is just `/entry` and `/api/cell`, and the two CLIs stay on the `enforce=False` default (both are admin tools, and refusing to import hours somebody worked would corrupt the record to protect a number). The exemption is passed *in* as `enforce=not is_admin` rather than having `notion_ops` reach for `auth`. Two rules the arithmetic lives on, both tested: **`set_cell` replaces rather than adds**, so the check compares the *delta* (counting duplicate rows it's about to fold together) — checking the submitted hours would refuse ordinary grid corrections all over a busy project; and **a write that lowers a project's month total is never refused**, or a project over its cap could never be corrected. Usage is keyed on the entry's own `Date`, so a September backfill against an August date spends August. `/budgets` is one calendar month (`_period_range` reused) built from **one** `entries_between` grouped in Python — one query per project would be 37 round trips on a free Render instance — with budgeted rows sorted trouble-first and unbudgeted ones left alphabetical below, because the first sitting on that page is ~37 numbers typed by hand and a list that reorders under the cursor is unusable. The real payoff is the meter on the log form (`GET /api/budget/status`): Harvest's whole failure mode is that budget feedback arrives next morning by email to someone other than the person logging the hours, and this lands at the moment of the decision — which is also why it shows a budget to a non-admin member, since a limit you can't see is a trap. Alerts fire at the write that crosses (there is no scheduler here), once per project per month via the `Budget notified` stamp, behind their own `BUDGET_ALERTS_ENABLED` switch, and a send failure is logged and swallowed. A hard cap only ever binds this app's UI — the CLIs and Notion itself write entries directly — so **`/budgets` is the real control and the cap is a nudge**. No new database, so no `databases.json`/Render id wiring. `tests/test_budgets.py` (36 checks, no Notion calls, no pytest).
- **The app has no native dialogs** (`zAlert` / `zConfirm` in `base.html`, `dialog.zdlg` in `style.css`): `window.alert`/`window.confirm` are drawn by the browser above the page — wrong typeface, "hours-znlove.onrender.com says" as a heading, and on desktop Chrome pinned to the top of the window, nowhere near what was clicked. The replacements are one `<dialog>` rendered by `base.html` on every page, so they trap focus, close on Esc and stack above another open dialog (the assign popover), while sitting centred in the viewport and looking like the rest of the app. Both return a **Promise** — every call site reads `await zConfirm(…)` where it read `confirm(…)`, which is why each one lives in an `async` function; `zAlert` may be left un-awaited. Options are `{title, ok, cancel, danger}`: a destructive question passes `danger: true` and puts the verb on the button ("Delete"), so the wording carries the consequence and the button carries the warning. **Deliberately not built on `<form method="dialog">`**: that form sets `returnValue` but the `close` event a promise must wait on doesn't reliably follow it, and a confirm whose promise never settles is a button that silently does nothing — the buttons call back directly instead, with the `cancel` event covering Esc.
- **No Notion views via API**: Form and reporting views can only be created in the Notion UI, never programmatically.

## Deploy

Push to `main` → Render auto-deploys (blueprint in `render.yaml`, start command `uvicorn web.app:app`). Secrets are set in the Render dashboard, not in the repo. A launchd job on this machine (`com.jp.hours-keepalive`) pings `/healthz` every 10 min to keep the free instance warm.
